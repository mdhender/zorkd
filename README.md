# Zork Server

A headless, request-oriented server for running the original Infocom **Zork I**, **Zork II**, and **Zork III** games.

The server executes the original Z-machine story files rather than reimplementing the games. Version 3 execution comes from [`github.com/maloquacious/zmachine`](https://github.com/maloquacious/zmachine); this project is its host, providing a network-facing application, durable session state, and the terminal the player actually sees.

## Goals

The project is intentionally narrow.

It exists to:

* run Zork I, Zork II, and Zork III;
* execute the original `.z3` story files;
* support independent game sessions;
* accept player input one request at a time;
* return the text generated by the game;
* persist game state between requests;
* stay small enough that the whole path from an HTTP request to a line of Zork can be understood and tested.

It is **not** an interactive-fiction platform, and it is **not** a Z-machine project. The interpreter is a dependency.

## Architecture

The server treats each player command as an independent execution request.

Conceptually:

```text
             request
                │
                ▼
        ┌────────────────┐
        │   Web Server   │
        └───────┬────────┘
                │
                ▼
        ┌────────────────┐
        │  Game Service  │
        │ intercept /    │
        │ render / store │
        └───────┬────────┘
                │
       load story + state
                │
                ▼
        ┌────────────────┐
        │    zmachine    │
        │ (external pkg) │
        └───────┬────────┘
                │
          run until input
                │
                ▼
       output + new state
                │
                ▼
        ┌────────────────┐
        │  State Store   │
        └────────────────┘
```

Execution is **headless and request-oriented**.

Nothing owns a terminal, keeps a permanently running interpreter process, or assumes an interactive command loop.

For each request, the application:

1. obtains the immutable `*zmachine.Story`, loaded once at startup;
2. loads the session's saved state;
3. creates a machine with `zmachine.New`;
4. restores the state and supplies the player's command;
5. executes until the game next requests input;
6. collects the generated output and status line;
7. persists the new state;
8. discards the machine.

A new game follows the same model but calls `Start` instead of `Restore` + `Run`, beginning from the story's initial state.

Rebuilding the machine every turn is observably identical to keeping one open — the engine's integration tests assert exactly that — so nothing has to stay resident between turns.

## The Engine

```text
github.com/maloquacious/zmachine v0.2.0
```

Pin the tag. The engine is `v0.x`, its exported API has already moved once, and a minor bump may break the build before `v1.0.0`. Requires Go 1.26 or later.

The engine provides the complete Version 3 opcode set, memory, objects and properties, the dictionary, text decoding, call frames, random numbers, input boundaries, and resumable state. It treats story files and saved states as hostile binary input: malformed data is an error, never a panic.

Its compatibility is validated on Zork I, II, and III, and differentially against dfrotz on Zork I — transcripts, status lines, and game state all match, and dfrotz successfully resumes a state this engine wrote.

Engine bugs are reported upstream at [maloquacious/zmachine](https://github.com/maloquacious/zmachine/issues) rather than worked around here. The most useful report is the story file, the exact sequence of inputs, and the saved state from the turn before the failure.

The engine implements Version 3 and is written against Standard 1.1, but deliberately leaves the header's standard revision number unset. Do not describe it as Standard 1.1 conformant.

## What This Project Owns

The engine deliberately stops at the edge of the screen. Everything past it is ours:

* **Rendering.** No word wrapping, no screen width, no cursor model. Story output arrives with its whitespace preserved exactly, and the roughly 80-column terminal is built here.
* **The upper window and status line.** Reported as data, never printed. Presentation is ours.
* **Save and restore.** In-story `SAVE` and `RESTORE` report failure without branching — legal Version 3 behavior, but the player would just see `Failed.` The application intercepts those commands before they reach the engine and wires them to session storage.
* **Transport, users, persistence, transactions, retries, concurrency control.** The engine has no filesystem, no network, and no environment.

Each story file name carries the release and serial number from the story's own header, because a saved state only restores against the exact story it was made from. See
[games/README.md](games/README.md).

The files originate from the historical Infocom source repositories:

* `historicalsource/zork1`
* `historicalsource/zork2`

## Embedded Games

The story files are embedded into the executable by the `games` package:

```go
//go:embed zork1/zork1-r119-880429.z3
var zork1 []byte
```

Deployment is therefore the binary and its database, and a server cannot come up missing the game it was meant to serve. The three images are about 267 KB together.

`games` is the only package that names a story file. Everything downstream takes them as data.

Story images are immutable application assets. `zmachine.LoadStory` copies the image it is given and validates the whole thing before returning, so the embedded bytes are never at risk from execution.

Each story is loaded once, at startup, and the resulting `*Story` is shared by every session playing that game. Creating a machine from it is cheap — it copies only dynamic memory, 11,282 bytes of Zork I's 86,838.

Sessions are keyed by a SHA-256 over the story image. Release and serial identify an *edition* rather than a file, and early Version 3 stories carry no checksum at all.

## Playing From the Terminal

`cmd/zorkplay` drives the turn cycle without a web server, which keeps engine and state debugging separate from web debugging:

```text
$ go run ./cmd/zorkplay zork1
$ go run ./cmd/zorkplay -list
$ go run ./cmd/zorkplay -seed 1988 zork2
```

The game defaults to `zork1` and is chosen by library id, never by path — `games` is the only place a story file is named. The machine is rebuilt from the story and the previous turn's state on every command, exactly as the server will do it, so a bug that only appears when a machine is thrown away appears here too. The session's state lives in memory; durable persistence is the server's job.

`-seed` makes a session reproducible, which is what makes a reported turn worth reporting. `-timeout` and `-limit` set the two bounds on a turn, `-width` sets the column count the story text is wrapped to, and `-v` sends engine diagnostics to stderr.

## Session State

Between turns, a session is a blob of bytes and the identity of the story they belong to.

That blob is complete and self-contained — not a delta, not a link in a chain — so the most recent one is the only one a session needs. Nothing has to be replayed, and states may be deleted in any order. A Zork I state is 356 bytes at the opening prompt and around 500 a few turns in.

```text
story + saved state + player input
                │
                ▼
           one machine
                │
                ▼
       output + new state
```

The bytes are opaque. This project does not parse them, edit them, or reach into them for the score or the room name — the engine reports those separately. They restore for as long as the story file is byte-identical, whatever engine version wrote them, so stored state never needs migrating across an upgrade.

A game session is therefore durable without a long-running interpreter process.

## Storage

SQLite, in WAL mode, through `zombiezen.com/go/sqlite`. Access is explicit and small — statements are written out, and the schema is built by versioned migrations embedded from `migrations/`, tracked in SQLite's own `user_version`. There is no ORM.

The state is written whole and read back whole. No column is derived from it, the schema will not accept a live game with nothing stored for it, and `NULL` means the story halted rather than the state going missing.

Every turn's write is conditional on the version it read, so a turn that lost a race is refused instead of overwriting the one that won.

## Session Model

A session identifies:

* the game being played;
* its current persisted state;
* application metadata needed by the server.

The story image itself is not copied into every session.

Multiple sessions playing Zork I share the same immutable story while maintaining completely independent mutable state. Two players in the same room of the same game cannot see each other.

Concurrency *between* sessions is free. Concurrency *within* one session is a correctness problem this application solves, with a per-session lock and a conditional write — two turns starting from the same stored state would otherwise both succeed, and one would silently vanish.

## Project Principles

### Prefer boring Go

Use the standard library where it is sufficient.

Dependencies should solve concrete problems rather than provide frameworks around simple functionality. The engine is the model: it is the whole interpreter, tested and fuzzed upstream, and writing it here would be the project.

### Host, not interpreter

Supply input, render output, store state. Z-machine behavior belongs to the engine, and a fix for it belongs upstream.

### Separate execution from transport

HTTP handlers do not import the engine.

A caller should be able to execute a turn without starting an HTTP server.

### Make execution reproducible

Given the same:

```text
story + saved state + input
```

the result is the same output and the same new state, except where Z-machine semantics explicitly involve nondeterminism. The random generator's state travels inside the saved state, so a resumed session continues its sequence rather than starting a fresh one, and tests can pin it with a seed.

### Treat saves as data

Session state is persistent game state, not an opaque interpreter process. It is storable, replaceable, and independent of any running machine — but it is not ours to interpret.

## Testing

Tests emphasize observable behavior, and they test *this* project. The engine has its own suite — 715 tests under `-race`, six fuzz targets, and a differential comparison against dfrotz — and duplicating it here buys nothing.

At minimum, test:

* the turn cycle: create, restore, run, persist, discard;
* that a rebuilt-and-restored machine continues identically to one kept alive;
* that a failed, cancelled, or timed-out turn leaves the previous state intact;
* classification of every engine error class;
* word wrapping and status-line rendering;
* HTML escaping of story output;
* interception of `SAVE` and `RESTORE`;
* persistence, user isolation, and concurrent updates;
* complete command sequences against the actual Zork story files.

Integration tests using real Zork transcripts are particularly valuable.

For example:

```text
> open mailbox
Opening the small mailbox reveals a leaflet.

> read leaflet
...
```

Such tests exercise the complete path from player input through execution to rendered output.

## Non-Goals

Unless deliberately added to the project, the following are out of scope:

* reimplementing or forking the Z-machine engine;
* games beyond the Zork trilogy, whose compatibility is unproven here;
* Z-machine Versions 4–8;
* graphical Z-machine versions;
* terminal emulation;
* sound;
* Blorb;
* save import/export or interoperability with other interpreters;
* reaching into the saved-state format for any purpose;
* rebuilding the games from ZIL;
* modifying the original Zork game logic.

The measure of success is not:

> How much of the Z-machine specification do we implement?

It is:

> Can the server reliably run Zork I–III, one request at a time, with durable sessions?
