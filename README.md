# Zork Server

A headless, request-oriented server for running the original Infocom **Zork I**, **Zork II**, and **Zork III** games.

The server executes the original Z-machine story files rather than reimplementing the games. It provides a network-facing application around a small Version 3 Z-machine execution engine and persistent Quetzal save states.

## Goals

The project is intentionally narrow.

It exists to:

* run Zork I, Zork II, and Zork III;
* execute the original `.z3` story files;
* support independent game sessions;
* accept player input one request at a time;
* return the text generated by the game;
* persist game state between requests using Quetzal;
* remain small enough that the Z-machine implementation can be understood, tested, and maintained as part of the project.

It is **not** intended to become a general-purpose Z-machine interpreter.

## Architecture

The server treats each player command as an independent execution request.

Conceptually:

```text
             request
                │
                ▼
        ┌────────────────┐
        │   Web Server   │
        └───────┬────────┘
                │
                ▼
       load story + state
                │
                ▼
        ┌────────────────┐
        │ Z3 Execution   │
        │     Engine     │
        └───────┬────────┘
                │
          run until input
                │
                ▼
       output + new state
                │
                ▼
        ┌────────────────┐
        │ Quetzal Store  │
        └────────────────┘
```

The execution engine is deliberately **headless and request-oriented**.

It does not own a terminal, maintain a permanently running interpreter process, or assume an interactive command loop.

For each request, the application can:

1. obtain the immutable Z3 story image;
2. load the session's Quetzal state;
3. instantiate the Z-machine;
4. supply the player's command;
5. execute until the game next requests input;
6. collect generated output;
7. serialize the resulting state;
8. persist the new Quetzal save;
9. discard the VM instance.

A new game follows the same model but begins from the initial state of the story file rather than an existing Quetzal save.

## Story Files

The project uses the original compiled Z-machine story files:

```text
games/
    zork1/
        zork1.z3
        LICENSE
    zork2/
        zork2.z3
        LICENSE
    zork3/
        zork3.z3
        LICENSE
```

The files originate from the historical Infocom source repositories:

* `historicalsource/zork1`
* `historicalsource/zork2`
* `historicalsource/zork3`

The relevant upstream files are:

```text
zork1/COMPILED/zork1.z3
zork2/COMPILED/zork2.z3
zork3/COMPILED/zork3.z3
```

The upstream repositories are licensed under the MIT License and identify Microsoft as the copyright holder.

Keep the corresponding license notices with any copied story files.

The ZIL source trees and historical build systems are **not dependencies of this project**. We execute the compiled Z3 story images directly.

## Embedded Games

The story files may be embedded into the Go executable using `go:embed`.

For example:

```go
//go:embed games/zork1/zork1.z3
var zork1 []byte
```

Story images are immutable application assets.

A session must never modify the embedded story image. Any writable Z-machine memory required during execution belongs to the individual VM instance.

## Z-machine Scope

The execution engine targets **Z-machine Version 3**.

Compatibility with later Z-machine versions is not a project goal unless explicitly added in the future.

Implementation decisions should therefore favor:

* correctness for Zork I–III;
* simple code;
* deterministic execution;
* testability;
* clear separation between immutable story data and mutable VM state.

Do not add abstractions solely because a full Z-machine implementation might eventually require them.

## Quetzal Saves

Persistent session state uses the Quetzal save-file format.

Quetzal handling should remain independent of the web layer and, where practical, independent of the Z3 execution engine itself.

The expected relationship is:

```text
story image + Quetzal state + player input
                    │
                    ▼
               Z3 execution
                    │
                    ▼
            output + Quetzal state
```

This makes a game session durable without requiring a long-running interpreter process.

## Session Model

A session identifies:

* the game being played;
* its current persisted Z-machine state;
* application metadata needed by the server.

The story image itself does not need to be copied into every session.

Multiple sessions playing Zork I should share the same immutable Zork I story bytes while maintaining completely independent mutable state.

## Project Principles

### Prefer boring Go

Use the standard library where it is sufficient.

Dependencies should solve concrete problems rather than provide frameworks around simple functionality.

### Keep the interpreter small

Implement the Z-machine behavior required by the supported games.

Do not turn this project into an implementation of the complete modern Z-machine specification by accident.

### Separate execution from transport

The Z3 engine must not know about HTTP.

The web server must not implement Z-machine semantics.

A caller should be able to execute a turn without starting an HTTP server.

### Make execution reproducible

Given the same:

```text
story + saved state + input
```

the engine should produce the same resulting state and output, except where Z-machine semantics explicitly involve nondeterminism.

Any required randomness should be isolated and controllable for testing.

### Treat saves as data

Quetzal files are persistent game state, not opaque interpreter processes.

They should be testable, inspectable, replaceable, and portable where the Quetzal specification permits.

## Testing

Tests should emphasize observable behavior.

At minimum, test:

* Z3 instruction decoding;
* operand handling;
* branching;
* calls and returns;
* stack behavior;
* memory access;
* object and property operations;
* text decoding;
* input handling;
* output handling;
* Quetzal save/restore;
* execution boundaries;
* complete command sequences against the actual Zork story files.

Integration tests using real Zork transcripts are particularly valuable.

For example:

```text
> open mailbox
Opening the small mailbox reveals a leaflet.

> read leaflet
...
```

Such tests exercise the complete path from player input through Z-machine execution.

## Non-Goals

Unless deliberately added to the project, the following are out of scope:

* graphical Z-machine versions;
* terminal emulation;
* sound;
* Blorb;
* Z-machine Versions 4–8;
* arbitrary Interactive Fiction compatibility;
* rebuilding the games from ZIL;
* modifying the original Zork game logic;
* implementing a general-purpose Z-machine frontend.

The measure of success is not:

> How much of the Z-machine specification do we implement?

It is:

> Can the server reliably run Zork I–III, one request at a time, with durable sessions?
